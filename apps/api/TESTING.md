# Проверки первого сценария (FAT-129)

Контракт: [FAT-123](https://linear.app/sketchyy/issue/FAT-123).
Это локальная проверка Go API и отдельного режима mobile. Эксплуатационные
RPO/RTO, перенос Supabase, OAuth и семейные функции остаются в своих задачах.

## Воспроизведение автоматической проверки

Нужны Go из `.go-version`, Node.js, `npm ci` в корне и отдельная PostgreSQL 18.
Не загружайте `.env` текущего приложения. Команды из корня:

```sh
npm run db:up --workspace=@fatbook/api
npm run test:integration:local --workspace=@fatbook/api
npm run typegen:go --workspace=@fatbook/api-client
git diff --exit-code -- packages/api-client/src/go/schema.d.ts
npx turbo lint typecheck build --filter=@fatbook/api
npx turbo lint typecheck test --filter=web
npx turbo typecheck --filter=@fatbook/mobile --filter=@fatbook/api-client --filter=@fatbook/shared
npx tsc --noEmit -p packages/shared/tsconfig.json
```

Для другой отдельной PostgreSQL администратор заранее выполняет
`apps/api/local/init.sql`, затем задаёт `API_TEST_DATABASE_URL` и запускает
`npm run test:integration --workspace=@fatbook/api`. Административная роль должна
уметь создавать/удалять тестовые БД и завершать их соединения. Не используйте
действующую БД приложения. Приёмка создаёт и удаляет только БД `fatbook_test_*`.

Каждый интеграционный тест применяет goose-миграции к новой БД. Seed готовит
два аккаунта, два общих продукта и по приватному продукту. `test:integration`
считает ошибкой отсутствие DSN, пропущенный тест, ноль выполненных тестов
или ошибку Go. CI выполняет этот же набор на чистом контейнере PostgreSQL.
Обычный `go test` без DSN по-прежнему допускает явный пропуск интеграции.

## Ручная проверка mobile — требуется перед закрытием FAT-123/FAT-129

Автоматический TS-транспорт не подтверждает работу нативных экранов и SecureStore.
Запишите дату, устройство, commit, адрес API и результат каждого шага. Не сохраняйте
пароли и токены в отчёте. Невыполненные пункты оставляйте пустыми.

Подготовьте два аккаунта и запустите API по [README](README.md#локальный-запуск).
Пароли вводятся локально в `seed:local`. Входы: `alice@example.test` и
`bob@example.test`. Из `apps/mobile`:

```sh
EXPO_NO_DOTENV=1 EXPO_PUBLIC_BACKEND=go EXPO_PUBLIC_API_URL=http://127.0.0.1:8080 npm run dev
```

В iOS Simulator используйте `127.0.0.1`; в Android Emulator — `10.0.2.2`;
на телефоне — LAN-адрес компьютера. При Docker для телефона нужно отдельно
опубликовать порт в локальной сети. HTTP разрешён только при `__DEV__`;
вне разработки обязателен HTTPS.

Статус основного Go-сценария: **выполнен агентом через iOS MCP 18 октября 2026**
на iPhone 17 Pro, iOS 26.5, Expo Go 56.0.3. Проверена ветка FAT-129 после
исправления дат поверх `cf79cd9`; отдельная БД `fatbook_ios_fat129_20261018`,
API `http://127.0.0.1:8080`. Секреты и токены в отчёт не записывались.

Результаты прохода:

- A 200 г + B 300 г, готовый вес 400 г: рецепт POST 201; порция 150 г —
  13.125 / 6 / 26.25 / 223.125, дневник показывает 223 ккал.
- Полностью остановлены и снова запущены API и Expo Go с прежней БД:
  SecureStore восстановил вход, GET me и дневника — 200, порция сохранилась.
- Имя, иконка и готовый вес 250 г сохранены одним PUT; новая порция 150 г —
  21 / 9.6 / 42 / 357. Старая сохранила исходные имя, иконку и КБЖУ.
  Итог — 34.125 / 15.6 / 68.25 / 580.125 (с обычной погрешностью float64).
- Ошибка PUT оставила черновик. Потеря ответа POST после реального commit
  оставила форму с весом 150 г; явный повтор не создал третью порцию.
  Эти отказы воспроизведены временной диагностикой fetch без изменения кода приложения.
- Рецепт удалён, старая порция открылась из снимка без GET карточки блюда.
  Изменение на 100 г дало 148.75 ккал; после удаления этой порции итог — 357.
- При остановленном API видны ошибка и повтор, последние 357 ккал сохраняются.
  После запуска API повтор успешен без входа. Ошибка logout сохраняет вход;
  успешный повтор даёт 204. У Bob пустой день и своя библиотека без данных Alice.
  Очистка незавершённого черновика Alice проверена отдельным проходом того же режима.
- Для нового входа срок сессии временно уменьшен до 30 секунд: после реального
  истечения сервер вернул 401, приложение очистило вход. Настройка API восстановлена.
- В наблюдаемых fetch-запросах сценария были только адрес Go API и пути
  auth/dishes/eatings; Supabase-запросов не было. Заголовки и тела не записывались.
  Диагностические перехваты удалены; системный трафик симулятора не исследовался.

Найденные ошибки даты исправлены: Go-адаптер преобразует день UI `18-Oct-2026`
в API `2026-10-18` перед GET/POST; общий форматтер принимает ISO-даты карточки.
Регрессия проверяется существующим HTTP-тестом мобильного адаптера и тестами
публичных утилит; тестов UI-компонентов не добавлялось.

Отдельный ручной повтор прежнего Supabase-режима с конфигурацией владельца
**не выполнялся**; этот пункт ниже оставлен открытым. Прежний формат UI и
Supabase-адаптер сохранены; общие даты, web и оба клиента проходят обязательные
проверки. Полное переключение прежних пользователей остаётся задачей FAT-58.

## Граница поставки

Предыдущие части FAT-123 уже вошли в `main` отдельными PR; объединить их задним
числом в один integration PR нельзя. FAT-129 поставляется отдельным PR с приёмкой
поверх них. Ревью первого сценария охватывает код от `b246828` (до Go API)
и изменения FAT-129. FAT-123/FAT-129 не закрываются до слияния и выполнения ручных
пунктов основного Go-сценария. Более широкие FAT-56/57/58/121 и действующий Supabase RLS остаются
самостоятельными задачами.
